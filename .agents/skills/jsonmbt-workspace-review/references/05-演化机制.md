# 演化机制

> 本规程**在使用中自己长大**：每次审阅都可能撞到"下次还会遇到"的东西，把它沉淀回 `references/`。
> 但**无约束的自我修改会让规程腐烂成日志**——所以准入、格式、告知三者缺一不可。
> （本章承 Vitro 同名文件，写入映射换成本仓文件名。）

---

## 1 · 触发时机

**每次审阅收尾（写报告时）固定自问三句**：

1. 这轮有没有撞到**之前没记录过的**缺陷形态？（→ `03`）
2. 有没有撞到**之前没记录过的**审阅流程 / 工具坑？（→ `04`）
3. 有没有发明**之前没有的**探针手法、对拍方法、锚/闸审计套路？（→ `01` / `02` / `06`）

三问全否 ⇒ 本轮无演化，报告里写"本轮演化：无"。

> 不要为了"有产出"硬写。**零演化是正常结果**。

## 2 · 准入判据（全中才写）

| # | 判据 | 自检问法 |
|---|---|---|
| 1 | **可跨批次复现** | "这是这一次的偶发，还是下次换个批还会遇到？" |
| 2 | **有明确判据或查法** | "我能写出一句'怎么查'吗？写不出就是还没想清，别写。" |
| 3 | **对下一次有可操作价值** | "下一个人读到这条，能少走一段弯路吗？" |
| 4 | **实例写得出「不含当时数字」的版本** | 「把里面的测试数 / 日期 / 批次号全删掉，这条还站得住吗？」站不住 ⇒ 你记的是**现场**，不是**形态** |

**任一条不中 ⇒ 不写。**

## 3 · 明确禁止写入的内容

| 禁止 | 例子 | 为什么 |
|---|---|---|
| **一次性现场快照** | 具体 commit 哈希、某批文件数、"本轮 28 锚全绿" | 下次跑就不一样，写进去等于埋漂移 |
| **一次性测量值** | `PASS 28 / FAIL 0`、某条目的当时条数 | 数字最容易被顺手抄进实例——要留的是「形状」不是「当时绝对真值」 |
| **相对时间叙事** | "上轮""本批""此前""我第一版踩了" | 对次日或对 clone 的人无意义 |
| **当次审阅的结论本身** | "P1：降级器少一个转义臂" | 那是报告的内容，不是规程的内容 |
| **第二人称日记** | "我踩过""我因此误判" | 改成无人称的形态陈述 |
| **未经核实的猜测** | "可能是因为编译器……" | 规程里只放实证过的东西 |

**改写方向**：把"这次发生了什么"改写成"**这类事怎么判、怎么查**"。

## 4 · 各文件的追加格式

**保持目标文件的既有结构**，别另起一套。

- `03-缺陷形态清单.md`：按 A（锚）/ B（分叉）/ D（闸与文档）/ F（工具）分类（C 预留给"死面"，撞到再开）。**能归入既有类就归入**；确需开新类时说明理由。每条格式：
  ```
  ### X n · <形态名>
  - **判据**：…
  - **查法**：…
  - **实例**：（可写项目内真实位置**与可复现判据**——一条命令 / 一段注入写法 / 一个 `文件:行`；**不写**具体 commit / 批次 / 测试数）
  - **处方**（可选）：…
  ```
- `04-工具链与踩坑.md`：表格一行（坑 / 表现 / 处置），接既有编号。
- `01` / `02` / `06`：按各自现有小节风格追加，**不要破坏编号**（编号被交叉引用）。

## 5 · 变更纪律

1. **只追加，不改写既有条目。**
   - 既有条目被证明写错（不是补充，是错）⇒ **先问用户**，确认后改，并在该条后加 `> 纠正（来源：…）`。
   - 单纯"补一个新例子"不算纠正，直接追加。
2. **改完必须显式报告**：在当轮回复里列出【改了哪个文件 + 加了什么】，并在报告结构第 4 节"本轮演化"里重复一次。**静默修改视为违规。**
3. **每次演化追加一行到 `references/07-演化日志.md`**（格式见下）。
4. **一次审阅的演化总量**建议不超过 5 条。超出说明在把当轮报告塞进规程，回去按 §3 过滤。
5. **禁止顺手重构**：演化时不重排章节、改标题、统一措辞——那些单独提。
6. **同族合并优先**：新形态属既有条目的同族触发面 ⇒ 做成该条目的子项 / bullet，不新开编号；确需合并既有条目须**用户拍板**且判据零丢失。

## 6 · 演化日志格式（`07-演化日志.md`）

```markdown
| 日期 | 触发 | 落点 | 内容 |
|---|---|---|---|
| YYYY-MM-DD | 审阅某批时撞到 X | 03 · B4 | 新增"形态名"：判据 / 查法 |
```

- **触发**：一句话说清是什么事让你决定写它（这批做了什么，不写 commit）。
- **落点**：文件 + 条目标号。
- 日志**只追加**，禁止改写历史行。

## 7 · 为什么要"必须告知"

- 规程是**多人多 agent 共用**的判断依据。一次静默改动，可能让别人基于"以为没变"的规程继续做事。
- 用户是本规程的**最终责任人**：他有权知道判断依据变了什么。
- 演化本身也要**可回溯**——出问题时，得能查到"是哪次审阅把这条规则加进去的"。

## 8 · 演化与"不改代码"的边界

- 演化**只改本 skill 目录内的文件**（`SKILL.md` + `references/`）。
- **不得**以"演化"为名改动仓库内任何其它文件——`AGENTS.md`、`docs/PLAN.md`、`docs/MOONBIT_PITFALLS.md`、CI 配置都在外。
  - 通用 MoonBit 事实的正式归宿是 `MOONBIT_PITFALLS.md`（陷阱快照、编号对齐 Vitro）——**回灌它 = 仓库变更，先问用户**；演化只能先把该事实收进本 skill `04`。
- 本规程若需要仓库内同步（如 AGENTS.md 加路由行）⇒ 按仓库纪律走（先问用户）。
